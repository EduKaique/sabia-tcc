# Sabiá v0.1.0

**Data:** 2026-11-03

> **Pré-release.** Esta é a primeira versão do Sabiá e o projeto ainda não está finalizado.
> Ela já foi implantada em produção e usada numa aula, mas tem limitações conhecidas (listadas
> abaixo) e pode mudar bastante nas próximas versões.

## Resumo

O Sabiá é uma plataforma para ensinar programação com blocos, no estilo Scratch, com apoio de IA.
O professor cria turmas e atividades, convida os alunos por um código ou link e corrige as entregas,
com sugestões de uma IA quando quiser. O aluno entra pelo convite, resolve as atividades montando
blocos no navegador e envia a solução. Esta versão traz também o modo Jogo do Robô e uma página de relatórios.

## Destaques

### Para a escola (administrador)

- Cadastro de professores, com opção de desativar e reativar o acesso.
- Acesso pelo navegador, sem instalar nada nos computadores da escola.

### Para o professor

- **Turmas:** criar, editar e excluir turmas; cada turma tem um código e um link de convite. O professor
  também pode matricular e desmatricular alunos.
- **Atividades:** criar atividades com descrição formatada, pontuação e um gabarito montado no próprio
  editor de blocos; publicar quando estiver pronta e despublicar se precisar.
- **Jogo do Robô:** um modo de atividade em que o aluno guia um robô até o destino num tabuleiro,
  desviando de obstáculos. O professor escolhe um cenário pronto e pode limitar o número de blocos.
- **Gerar atividade com IA:** o professor descreve o que quer e recebe uma sugestão de atividade, com os
  blocos do gabarito já inseridos no editor.
- **Correção:** o professor vê o programa de cada aluno e lança nota e feedback. Pode pedir uma revisão
  da IA (resumo, nota sugerida, acertos e erros), mas a nota final é sempre dele. No Jogo do Robô, a
  correção reexecuta o percurso do aluno e sugere a nota.
- **Relatórios:** médias por atividade, distribuição de notas, progressão dos alunos e status das
  entregas de cada turma.

### Para o aluno

- Entrada pelo link de convite ou pelo código da turma, com primeiro acesso guiado (dados, avatar e senha).
- Nos acessos seguintes, login com a matrícula.
- Lista de atividades com o status de cada uma (pendente, em andamento, entregue, corrigida).
- Editor de blocos com visual de Scratch, painel de entrada e saída e botão para executar o programa
  antes de entregar.

## Infra e segurança

- **HTTPS por IP:** o servidor é acessado pelo IP público, sem domínio. O Caddy obtém e renova sozinho um
  certificado de IP do Let's Encrypt (validade curta, de cerca de 6 dias).
- **Imagens no GHCR:** o GitHub Actions roda os testes dos serviços Java e publica as imagens no GitHub
  Container Registry. O servidor só baixa as imagens e nunca compila nada. Em produção, use as tags `sha-xxxxxxx`.
- **Backups:** o `deploy/backup.sh` faz o dump do banco e guarda 7 dias. O deploy faz um backup antes de
  atualizar, e o `deploy/restore.sh --test` permite conferir se um backup restaura sem mexer no banco real.
- **Backend endurecido para produção:**
  - `JWT_SECRET` é obrigatório e precisa ter tamanho mínimo; valores padrão são recusados na subida.
  - Os dados de desenvolvimento (usuários e senhas de teste) não são carregados em produção. Os usuários
    iniciais vêm de variáveis de ambiente.
  - O token JWT é validado no gateway e de novo no serviço pedagógico.
  - Só o Caddy fica exposto: banco, serviços internos e documentação da API não são acessíveis de fora.
- **RabbitMQ opcional:** o serviço pedagógico funciona sem ele, e em produção ele fica desligado para
  economizar memória.
- **Sanitização de HTML:** as descrições das atividades passam pelo DOMPurify antes de aparecer na tela do aluno.
- **Chave do Gemini fora dos logs:** a chave vai num cabeçalho e as mensagens de erro são filtradas antes de
  serem registradas.

## Limitações conhecidas

- **Cota da IA:** a chave do Gemini usa a cota gratuita. Quando ela acaba, o ia-service retorna o código
  `COTA_IA_ESGOTADA`, mas o front ainda mostra só um erro genérico, sem explicar que a cota acabou.
- **Jogo do Robô:**
  - Não tem geração nem revisão com IA.
  - A simulação e o limite de blocos são verificados só no navegador; o servidor não reexecuta o percurso.
  - Só existem os cenários prontos; ainda não há editor de cenários.
- **Nota para o aluno:** a nota e o feedback são gravados e a API já os devolve, mas a tela do aluno
  ainda mostra só o aviso de que a atividade foi corrigida.
- **Troca de senha e perfil:** a troca obrigatória de senha e a edição de perfil existem na API, mas
  ainda não têm tela no front.
- **Testes do front:** o `jest` não está instalado, então `pnpm test` não roda e o CI do front faz só
  checagem de tipos, lint e build.
- **JSON malformado:** uma requisição com corpo JSON inválido recebe erro 500 em vez de 400 no auth-service
  e no serviço pedagógico.
- **Health check público:** `/api/health` é público e a resposta inclui as URLs internas dos serviços.
- **E-mail em modo `dev`:** com `EMAIL_PROVIDER=dev` (o padrão), o link de redefinição de senha é gravado
  no log do auth-service em vez de ser enviado. Em produção, use `smtp`.
- **Sem limite de requisições:** não há rate limit no gateway, no Caddy nem nas tentativas de login.
- **Senhas iniciais:** o tamanho mínimo das senhas dos usuários iniciais (`SABIA_*_SENHA`) é só uma
  recomendação do runbook e não é validado no código. Defina todas antes da primeira subida.

## Como atualizar

No servidor, de dentro do clone do repositório:

```bash
git pull
deploy/deploy.sh <tag>        # ex.: sha-xxxxxxx; faz backup antes
deploy/smoke.sh https://<IP>  # de outra máquina
```

Para voltar à versão anterior: `deploy/deploy.sh --rollback`. O rollback não desfaz mudanças no schema
do banco; se precisar, restaure o backup feito antes do deploy.

Passo a passo completo, primeiro deploy e diagnósticos: [Runbook de produção](../runbook-producao.md).
Lista detalhada das mudanças: [CHANGELOG](../../CHANGELOG.md).
